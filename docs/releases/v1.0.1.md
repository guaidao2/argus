### The UDP side of port 111 answered nothing

A UDP scan sends the payload that service is known to answer, then waits for any
reply; a port that says nothing stays `open|filtered`, and detection only runs on
ports that answered. Port 111 had no payload of its own and fell back to a single
`0x00` byte. A portmapper drops a datagram it cannot decode without a word, so
the reply never came: no fingerprint and no check for 111 was reachable over UDP,
and a scan could not tell "filtered" from "the payload was unreadable".

Port 111 now sends the portmap `DUMP` call it will answer. `udp/111` comes back
`open`, is identified and is reachable by the checks. The test pins both
directions: the real call gets an answer, and the one-byte datagram that used to
be sent still reads `open|filtered` — which is what that payload looked like from
the outside.

### A plugin's `service:` binding did nothing

`service: redis` on a check rule is how a rule follows a service onto whatever
port it turns up on. Built-in rules were indexed by service; plugin rules were
not: `AddYAMLFront` filed them under their ports and in the "applies everywhere"
list, but never in the service index. Both consequences were silent:

- a plugin check bound to a service never ran on a port the plugin did not name,
  so a working binding looked like a rule that simply did not match;
- if such a rule also had no `ports:`, it landed in the "applies everywhere"
  list and its probe was sent to **every open port of the scan** — the opposite
  of what a service binding means.

Plugin rules are indexed exactly like built-in ones now, and a check that binds
to a service is never applied to a port where that service was not identified.
Two tests cover it: the service-bound plugin check fires on the port where its
service was found, and the same check stays silent on the same port when nothing
identified the service.

### Releases come from a tag

`.github/workflows/release.yml` runs `gofmt`, `go vet` and the test suite, builds
the archives through the same `make package` path the 1.0.0 archives came from,
checks that every archive really contains a binary and that there are six of
them, writes `checksums.txt`, and publishes the release. The toolchain is the one
`go.mod` pins, so the build does not drift with whatever a runner happens to have.

The notes you are reading are a file in this repository, `docs/releases/v1.0.1.md`,
and the workflow refuses to publish a release whose notes file is missing: what a
release says about itself is written by hand, not summarised from commit
subjects.

### Also

  prints and failed on Windows. It checks the message catalog now, so every build

### 中文说明

**argus v1.0.1** —— 补丁版本：修掉两处让 111 端口"悄悄不完整"的接线 bug，并把发版交给
打 tag 的 CI 完成。

要点：**111 端口的 UDP 侧收不到任何应答。** UDP 扫描会发送该服务已知会回应的载荷再等
回复；不回话的端口就是 `open|filtered`，而检测只对回过话的端口运行。111 一直没有自己的
载荷，于是退化成单个 `0x00` 字节；portmapper 对无法解码的数据报一声不响地丢掉，所以回复
永远不会来——111 在 UDP 上的指纹与检测全部是不可达的死代码，扫描也无法区分"被过滤"和
"载荷读不懂"。现在 111 发送的是 portmapper 一定会应答的 `DUMP` 调用：`udp/111` 变成
`open`，能被识别，也能被检测到达。测试把两个方向都钉住了：真正的调用拿到应答，而过去发的
那个单字节数据报仍然读出 `open|filtered`——那正是它从外面看起来的样子。

**插件规则上的 `service:` 绑定不起作用。** `service: redis` 的语义是"这个服务出现在哪个
端口就跟着去".内置规则有服务索引，插件规则没有：`AddYAMLFront` 只把它们登记到端口和
"到处适用"列表里。两个后果都很安静：绑定服务的插件 check 在插件没写过的端口上永远不跑，
看起来就像"规则没命中"；而若它同时不写 `ports:`，就会落进"到处适用"，探测被发给**扫描中
的每一个开放端口**——正好是服务绑定的反面。现在插件规则的索引与内置规则完全一致，绑定
服务的 check 不会再被应用到手没识别出该服务的端口上。

**发版改为打 tag 自动完成。** CI 会跑 `gofmt`、`go vet` 与测试，用与 1.0.0 相同的
`make package` 路径打包，校验每个归档里确实有二进制、且正好六个，生成 `checksums.txt`
并发布；工具链用 `go.mod` 钉住的版本，不随 runner 漂移。你正在读的这份说明是仓库里的文件
`docs/releases/v1.0.1.md`，缺少说明文件时工作流会拒绝发布：一个版本如何描述自己，靠手写，
不是从 commit 主题里自动汇总出来的。

详细说明见 [README.zh-CN.md](https://github.com/guaidao2/argus/blob/main/README.zh-CN.md)，
插件文档在 `docs/plugin-guide.zh-CN.md`。每个压缩包内都包含二进制、两个 README、
`LICENSE` 与 `docs/` 下的插件指南。
